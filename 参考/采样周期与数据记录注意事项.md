# 采样周期与数据记录注意事项

本文档记录 `p0_current_consistency` 后续实验程序中必须注意的采样周期问题，避免再次把 Windows 程序延时误认为控制卡或电流读取能力限制。后续实验如发现新的采样、同步、数据记录问题，可以继续补充到本文档。

## 1. 已验证结论

在 `p0_sampling_period_probe.cpp` 中对 PC 侧采样循环进行了测速，数据文件为：

- `data/sampling/p0_sampling_period_probe.csv`

统计结果说明：

| 测试模式 | 采样周期中位数 | 平均周期 | 说明 |
|---|---:|---:|---|
| 纯 `QueryPerformanceCounter` 循环 | 约 0.0004 ms | 约 0.00047 ms | PC 计时开销很小 |
| 只读 `GTN_GetAtlTorque` | 约 0.049 ms | 约 0.052 ms | 单独读电机侧力矩很快 |
| 读位置 + 力矩 | 约 0.150 ms | 约 0.165 ms | 可达到 kHz 级采样 |
| 读完整实验字段，无 `Sleep` | 约 0.497 ms | 约 0.497 ms | 完整字段采集约 2 kHz |
| 读完整字段 + `Sleep(0)` | 约 0.497 ms | 约 0.500 ms | 基本不拖慢 |
| 读完整字段 + `Sleep(1)` | 约 15.59 ms | 约 15.60 ms | 这就是之前约 16 ms 采样周期的主要来源 |

因此，之前空载实验中出现的约 16 ms 采样周期，主要不是控制卡、驱动器或 `GTN_GetAtlTorque` 的速度限制，而是程序中使用 `Sleep(1)` 后，Windows 调度粒度导致实际休眠接近 15.6 ms。

## 2. 后续程序中不要这样写

不要在高频采样循环里直接使用：

```cpp
Sleep(1);
```

也不要假设 `Sleep(1)` 等于精确等待 1 ms。在普通 Windows 用户态程序里，它可能实际等待约 15.6 ms，导致采样周期大幅变慢。

如果程序还在循环中每个采样点都 `fprintf` 写 CSV，也会进一步引入不稳定延时。高速采样时应避免边采样边频繁写硬盘。

## 3. 推荐写法

### 3.1 使用高精度计时

程序开始时建议使用：

```cpp
timeBeginPeriod(1);
QueryPerformanceFrequency(&freq);
QueryPerformanceCounter(&t0);
```

程序结束前使用：

```cpp
timeEndPeriod(1);
```

时间戳优先使用 `QueryPerformanceCounter`，不要只依赖 `timeGetTime()`。

### 3.2 数据先写内存，实验结束后再写 CSV

推荐方式：

```cpp
std::vector<SampleRow> rows;
rows.reserve(expected_sample_count);

// 采样循环中只 push_back，不 fprintf
rows.push_back(row);

// 实验结束后统一写 CSV
writeCsv(rows);
```

这样可以避免磁盘写入把采样周期拉长或造成周期抖动。

### 3.3 如果只是让出 CPU，用 `Sleep(0)`

如果需要避免完全占满 CPU，可以在循环末尾使用：

```cpp
Sleep(0);
```

根据当前测试，`Sleep(0)` 对完整字段采样周期影响很小，仍接近 0.5 ms。但它不是严格定时器，只适合让出时间片，不适合作为精确采样周期控制。

### 3.4 如果需要固定采样周期，用 QPC 主动定时

例如目标 1 ms 采样周期：

```cpp
const double samplePeriodS = 0.001;
LARGE_INTEGER freq, t0;
QueryPerformanceFrequency(&freq);
QueryPerformanceCounter(&t0);

for (int k = 0; k < sampleCount; ++k) {
    double targetTimeS = k * samplePeriodS;

    while (true) {
        LARGE_INTEGER now;
        QueryPerformanceCounter(&now);
        double t = (double)(now.QuadPart - t0.QuadPart) / (double)freq.QuadPart;
        if (t >= targetTimeS) break;

        // 离目标时间还比较远时可以 Sleep(0)，接近目标时忙等
        if (targetTimeS - t > 0.0002) {
            Sleep(0);
        }
    }

    // read GTN signals here
}
```

注意：这只能改善 PC 侧采样时间戳和读取频率，并不保证 Windows 用户态具备严格实时性。

## 4. 推荐实验采样频率

根据当前测试：

- 只读 `GTN_GetAtlTorque`：PC 侧循环可到约 0.05 ms。
- 读取完整实验字段：PC 侧循环可到约 0.5 ms。
- 后续一般接触/空载建模实验，建议先使用 1 ms 或 2 ms 目标采样周期。
- 如果只是低速重复轨迹，2 ms 或 5 ms 也足够。
- 如果要做快速接触、正弦力任务、碰撞瞬态分析，建议至少记录到 1 ms 量级，并保存真实 `dt`。

CSV 中必须保留真实时间戳，不要假定采样周期严格等于设定值。

## 5. 必须区分两件事

### 5.1 PC 侧采样周期

这是程序调用 API、读取变量、写入内存的循环周期。本次测试说明 PC 侧完整字段读取可以达到约 0.5 ms。

### 5.2 驱动器/控制卡内部数据刷新周期

即使 PC 侧 0.5 ms 读一次，也不代表电流、力矩、编码器等内部变量每 0.5 ms 都真实更新一次。真实刷新率取决于驱动器、控制卡、EtherCAT/PDO、内部缓存和变量来源。

因此后续还需要通过数据中相邻样本是否重复、信号阶梯变化、时间戳与轨迹相位一致性等方式判断真实有效刷新率。

## 6. 后续写实验程序时的检查清单

新实验程序完成后，至少检查：

1. 是否误用了 `Sleep(1)` 作为采样周期控制。
2. 是否在采样循环中频繁 `fprintf` 写 CSV。
3. 是否使用 `QueryPerformanceCounter` 保存真实时间戳。
4. 是否保存了每个样本的真实 `dt` 或可由 `time_s` 计算 `dt`。
5. 是否记录 `current_read_ret` / `ret_summary`，确认读取没有报错。
6. 是否记录限位、轴状态、规划状态，便于定位异常。
7. 是否区分“采样记录频率”和“控制闭环实时性”。

## 7. 当前建议

后续所有空载建模、接触验证、快速接触实验程序，默认采用：

- `QueryPerformanceCounter` 计时；
- 采样循环内只读 API 并写入内存；
- 实验结束后统一写 CSV；
- 不使用 `Sleep(1)` 控制采样；
- 若需要让出 CPU，优先使用 `Sleep(0)`；
- 若需要目标采样周期，使用 QPC 主动定时；
- CSV 必须保留真实 `time_s`。

这样可以避免把 Windows 调度延时误判为空载模型误差、控制卡性能限制或传感器读取限制。
